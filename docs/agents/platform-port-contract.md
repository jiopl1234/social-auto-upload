# Platform delivery integration contract

Tickets 07/09/11 use `orchestrator.platforms.base.BrowserDeliveryAdapter`. Root owns this common implementation and CLI registration. Platform workers own the concrete page ports and platform-specific tests. Tickets 08/10 begin only after 07/09 close.

Each port has `platform`, `content_types: frozenset[str]`, `capability_version: str`, `verification_scope: str` (`unverified`, `local_fixture`, or an explicitly implemented concrete live scope) and async methods:

```python
async def navigate(self, page, content_type: str, *, readonly: bool) -> None: ...
async def identify_account(self, page) -> str: ...
async def check_challenge(self, page) -> None: ...
async def upload(self, page, manifest) -> None: ...
async def wait_media(self, page, manifest) -> None: ...
async def apply_fields(self, page, manifest) -> None: ...
async def readback(self, page) -> dict: ...
async def arm_submission(self, page) -> None: ...
async def submit_once(self, page) -> dict | None: ...
async def list_works(self, page, content_type: str) -> list[dict]: ...
```

The adapter constructor is `BrowserDeliveryAdapter(runtime_dir: Path, port_factory: Callable[[], PagePort], *, session_factory: Callable[[ExecutionContext], BrowserSession] | None = None, verification_wait: float = 0, on_verification: Callable[[str], None] | None = None)`. Each attempt creates its own port and session. A local fixture port must navigate only a file/loopback URL; the shared adapter also guards origin and blocks external network requests. Default unverified production ports return `UNSUPPORTED` before opening a browser. There is no CLI flag to bypass missing production evidence.

The concrete DouyinVideoPort alone may use the fixed Douyin creator origin. Its available scope is original/non-AI video, title/body, immediate public publication and source-frame covers. Other fields fail before browser creation. `can_execute` reports this implemented scope separately from full CLI live-publication acceptance (`production_verified`). The latter remains false until that exact end-to-end path is exercised.

The concrete ChannelsVideoPreparationPort is permitted at its fixed Channels creator origin only through PreparationOnlyAdapter. ChannelsVideoPort separately uses `channels_video_v1` at that exact origin. Supported scope is one original/non-AI video up to 32 MiB, a 6–16 UTF-16-unit short title, single-paragraph description, immediate public submission and default cover, with no topics/mentions/location/link/activity/collection/custom cover/declarations. Observed upload parts, server completion and source-linked decoded previews are required. The editor's own HEVC processing RPC may run only before submission; its result query is read-only. A disabled publication control or visible upload failure prevents READY, even when source preview decodes.

Before a new Channels preparation, the validated storage-state snapshot excludes only the observed `AssistantUploadedInfoStorageKey_<digits>` resume cache at the exact origin. Authentication, account and device entries remain unchanged. BrowserSession applies this pure in-memory filter before browser creation; it does not introduce an injected global network route or reopen the session file. Recovery and inspection retain the original state and never apply this filter.

Channels accepts observed HTTP 200/201 positive envelopes. The live creation reply contains outer `errCode=0` and inner `data.baseResp.errcode=0` but no work ID. Preserve that acknowledgement separately and leave `receipt_id=null`; never manufacture a creation receipt ID from a list. Without a receipt ID, require that same attempt's positive acknowledgement and saved source SHA256/MD5, an unfiltered complete first creator page (`currentPage=1`, `userpageType=11`, matching authenticated principal, totalCount equals unique returned rows, continueFlag=false), no more than 10 rows, independent readable details for every row and exactly one matching work. With an ID, require the same ID and independent detail. Signed media URLs may change during processing; match independently returned original MD5 rather than asserting upload-key equality or inventing remote SHA256.

Channels detail does not expose author ID in the observed live response. When absent, account provenance is explicitly `authenticated_creator_list`: independently observed `auth_data` identity, unchanged creator authentication and that identity's own list request. A present conflicting detail author is rejected. Bind the retained list envelope after identity is available so response arrival order cannot change the result. Exact title/body, source MD5, creation time and normal/public settings remain mandatory. Report `ACCEPTED` conservatively, or `IN_REVIEW` when that state is explicitly observed; these do not establish moderation or distribution success. Read-only navigation uses explicit read-RPC allowlists because these APIs use POST, and blocks drafts, publication and new processing calls. `inspect-work --platform tencent` uses this same ownership, budget and read-only detail path. Post-click verification pauses the account with uncertain delivery; Channels has no human-wait implementation yet. The authorized `4.mp4` first CLI run completed submission, inline positive acknowledgement persistence and independent work confirmation in one attempt. Its limited scope now reports `production_verified=true` and `live_cli_submission_verified=true`; this does not establish other accounts, field combinations, challenge-free operation, moderation or distribution outcomes. See `docs/audit/channels-cli-video-2026-10-01.md`.

The concrete XiaohongshuVideoPreparationPort may use its fixed creator origin only through PreparationOnlyAdapter. Its scope is one original/non-AI video up to 32 MiB, title/body, public/immediate editor defaults, no requested topics/collection/custom cover/declarations. The raw delivery adapter rejects this preparation scope before browser creation; the wrapper and its underlying adapter cannot arm or submit. The separate concrete XiaohongshuVideoPort uses `xiaohongshu_video_v1`, the same exact creator origin and the observed edith API origin for limited delivery. Capability reporting separates live submission, details, receipt observation and saved-receipt recovery. `3.mp4` supplies a positive live creation response and same-attempt CLI receipt recovery. Inline receipt persistence with the corrected live envelope still has only offline acceptance, so `production_verified=false` and `live_inline_receipt_persistence` remain explicit.

Xiaohongshu preparation observes `/api/galaxy/user/info` for the stable account and checks the observed creator authentication cookies on each guard. Source fingerprints are computed in a watched child under the upload stage budget. Upload evidence requires browser-generated permitted object requests: each part's actual body SHA256 and MD5/ETag, continuous numbered parts under one upload transaction, a complete matching completion request, and a positive server acknowledgement of the same object. The frontend dynamically selects chunk sizes (2/3/5 MiB observed); a watched child in the cumulative processing budget verifies the actual ordered partition against the unchanged source, including out-of-order parts. At most 64 parts and 32 MiB are accepted, with total bytes equal to the source. Conflicting duplicate parts fail closed. Its final multipart ETag is opaque; do not assume the S3 formula. Local blob playback is checked against the source bytes as a separate decoder observation; this does not claim remote post-publication transcoding or moderation success. Tiptap plain paragraphs and explicit line breaks are read without trimming or collapsing user whitespace; decorated/unknown structures fail closed.

A preparation port sets `resources_unconfirmed` when its watched helper shutdown cannot be verified. BrowserDeliveryAdapter propagates this to BrowserSession before cleanup so a successfully closed browser cannot clear an unconfirmed helper's ownership fence.

Douyin upload evidence binds the selected source snapshot to CommitUploadInner Vid/VideoMeta and a matching processed preview, and stores the Vid/hash/attempt link before READY. Remote works expose Vid, not source SHA256. Their matching therefore requires the same attempt's saved receipt ID and uploaded Vid, stable author, independently observed title/body, known result and integer-second creation time. Do not copy a source SHA into a remote observation. Missing receipts or fields remain UNKNOWN_COMMIT. Source-frame default cover and empty optional settings are checked in the editor; remote media/cover hashes are not claimed.

Xiaohongshu stores the watched child's source SHA256 and MD5 with this attempt's observed upload key before READY. Its independent GET detail exposes a different canonical `video_info.file_id` and original `video_info.media_v2.video.md5`; never require the temporary key to equal the canonical ID or invent a remote SHA256. Match remote MD5, stable author, exact title/body, public/immediate settings, known state and integer-second post time. A present receipt must match the work ID. Without a receipt, require an unfiltered complete first page (`tab=0&page=0`, `page=-1`, checked all-tag count equals unique returned rows), at most 100 rows/10 videos, readable details for every video and exactly one matching work. Missing/unrecognized evidence remains UNKNOWN_COMMIT. Legacy MD5 enrichment is allowed only during owner-guarded UNKNOWN_COMMIT recovery after a watched read verifies the persisted source SHA256; it changes no receipt, attempt, submission state or action count. Subsequent recovery uses persisted fingerprints without rereading new-task source files.

Xiaohongshu read-only navigation blocks non-GET/HEAD/OPTIONS requests to both creator and observed API origins, including drafts and update endpoints. Detail is loaded via the real application's own authenticated GET on the edit view; never fill, save or update that view. Creation receipts require success=true plus an integer zero status (`result=0` in the live creator reply, or compatible `code=0`) and a unique valid server ID. Boolean statuses, conflicting statuses/IDs and missing positive status fail closed. Receipt does not establish publication alone. Save only allowed semantic response fields, never raw signed responses. The first real attempt has no saved receipt; `3.mp4` captured the live positive format. Explicit `jobs recover-receipt` holds the account maintenance lease and can reparse only one saved live response belonging to an already COMPLETED/CONFIRMED attempt. Its ID must match independent confirmed work; only receipt ID and recovery provenance may change. No browser, new attempt, submission-state change or action-count change is permitted.

Prepare navigates, checks challenge and stable identity, uploads, waits for positive per-file processing evidence, applies and reads fields, rechecks identity/challenge, saves state, then returns the actual seven-field readback. Each operation runs under the existing cumulative stage budget. The adapter's optional `verify_ready(context)` hook rechecks identity/challenge/readback against persisted ready metadata and arms the final control before worker persists SUBMITTING. Submit then invokes exactly one final action; ownership and SUBMITTING persistence remain in worker. Reconciliation navigates read-only and returns independent work observations; no copying job metadata to manufacture evidence. Recovery can open a new session without original media files.

Managed session loading and validation run in a watched, terminable child within the navigation budget. The browser receives that validated in-memory snapshot, not a filename that its driver would read again. Receipt waiting must continue to observe challenges after the final action; an existing editor is checked before reconciliation navigation can remove a prompt. Authentication errors after SUBMITTING pause the account while preserving uncertain delivery, rather than treating the prompt as proof of success or permission to resubmit.

An explicit `jobs run --job ... --headed --verification-wait 1..600` may keep the original Douyin or Xiaohongshu video submission open for human verification. Default is off; prepare-only, batches, unsupported paths and already-submitted jobs cannot enable it through the CLI. The adapter pauses the account and persists a verification event immediately, then uses the port's `wait_for_receipt(page)` to observe the same submission without another final action. Repeated prompts share one timeout, subordinate to the existing cumulative stage/total budgets, cancellation, ownership fence and cleanup reserve. Never automate the challenge, dismiss it or refresh it. Receipt, refreshed stable identity and saved session precede the verified event. Only independently confirmed work and clean delivery finalization may clear this attempt's exact verification pause. All uncertain outcomes keep the account paused. Notices use stderr and fixed state strings; no challenge payload, QR content or session secrets enter diagnostics. Xiaohongshu human-wait behavior currently has synthetic acceptance, not a real human-verification case.

If an unrecognized dialog appears after the human prompt has resolved and a valid receipt was already observed, leave the editor page and dialog untouched. A separate page in the same guarded browser context may navigate to the read-only work list; it must obtain a new site-observed stable identity, save the session and pass the ordinary independent receipt/Vid/work checks. The original attempt's deadline, ownership, cleanup and account pause still apply. Without that receipt or with missing work, retain UNKNOWN_COMMIT and pause. A secondary page must register its own response observer so it cannot rely on responses from the original page.

A port that starts a receipt observer exposes it as `receipt_task`. The adapter captures the port for the attempt and registers this child with `ExecutionBudget.track` as submission unwinds, even if browser cleanup clears the adapter's port field. Unfinished observers participate in the existing resource-fence check; their late exceptions are consumed without printing browser details.

Ports must preserve title/body, match exact topic candidates, apply declarations only when explicit, fail closed for missing required controls, and never remove unknown overlays. Actual readback contains `title`, `body`, `tags`, `media`, `cover`, `collection`, `declarations`. Media entries contain kind/sha256 only after a positive, traceable per-file upload observation. Work observations match `orchestrator/delivery.py` and must include observed stable account/type/id/status/time/metadata and media fingerprint when no receipt ID exists. Local DOM fixtures are synthetic contracts, not a claim that platform production DOM exposes these fields.

Keep real creator selectors from current legacy code as documented candidates. If a stable account or work evidence source is unknown, express that in capability metadata and leave live execution restricted; do not invent attributes and claim live support. Legacy unsafe publishing entry points must not remain a parallel bypass of the task protocol. Preserve parsing and positional constructor meanings; an explicit migration error is preferable to silently dropping facts or returning success.
